# Save/Load via localStorage

Status: in progress

## Design

**What you'll see:** the game remembers you. Close the tab and reopen the page and you're back
on the same map with your villagers, buildings, techs and age where you left them. The top
bar gets a `Save` button; `N` (New map) and the `New game` button on the victory overlay
start a fresh game and overwrite the save.

**How it works:** `saveGame(path, Game)` in section 4 produces
`{ version, seed, writtenAt, state }` — JSON of the plain `Game` minus the DOM-only fields
(`dom`/`view`/`mm`/`mmBase`/`toastMsg`/`toastAt`/`pingAt`/`frame`) and minus `pathQueries`;
`Game.techs` (a `Set`) and `Game.blocks` (a `Map`) get explicit encode and decode.
`loadGame(path, raw)` validates the `version` and the shape, and on a mismatch, a bad payload
or a missing key falls back to the current `resetGame(Game)` behaviour instead of throwing; a
successful load re-runs `rebuildBlocks` and bumps `Game.mapEpoch` so routing matches the
loaded buildings. A `VERSION` constant in `CFG` is the stamp; any future field change carries
a migration function rather than silently discarding a save. Autosave fires on a debounced
tick after a committed change (build completes, unit trains, tech researches, age up, combat
death, order change) plus a slow interval, so nothing is saved every frame. `localStorage` is
read/written through one pair of helpers that no-op safely when `localStorage` is unavailable
(the node harness and `render-preview.js` run without a DOM). `New game` / `N` and the result
overlay's button clear the slot.

**Not in this round:** multiple save slots, cloud sync, share codes (P2 item 12 replay/seed),
touch layout, sound.

**How we check it:** a harness section for the save contract — `save -> load -> save` produces
byte-identical JSON; every observable field (units, buildings, resources, age, techs, result,
camera, nextId, time) equals its pre-save value after a load; the `Set`/`Map` fields survive
the round trip; a wrong or missing `version` is refused and resets the game rather than
throwing; a corrupt string is refused the same way; and the loaded game keeps running (a unit
mid-order still finishes its route, the HUD renders the same `data-state`). `preview.png` must
come out byte-identical, and `check-stats` / `audit-line-refs` stay green.

**Hard constraints that survive from `AGENTS.md`:** the game stays one `index.html`; no
framework, no build step, no new image files beyond the one `assets/sprites.png` atlas;
`index.html` is patched, never rewritten; section 4 stays DOM-free; every task names a
proving check and the `Map of this file` banner stays truthful.

Decisions this plan makes where the design left room (fixed here so the executor does not have
to re-decide):

- **Every number the game tunes lives in `data/units.json`** (`AGENTS.md`: section 1 is
  generated). `tools/check-stats.mjs:136-144` renders scalar `cfg` values with `num()`, so
  only *numbers* can go in `CFG`; `VERSION`, `AUTOSAVE_DEBOUNCE` and `AUTOSAVE_EVERY` are
  numbers and go there, and the slot name becomes a plain section-4 const `SAVE_PATH` beside
  `const AGES` (`index.html:375`) — the same way `T`, `PAL`, `AGES` and `DIRS8` are declared
  outside the generated blocks.
- **`saveGame(path, Game, at = now())`** — the design's two-argument call still works. The
  third argument pins `writtenAt`; without it the stamp moves on every call and the
  `save -> load -> save` byte-identity check could never pass.
- **The payload is state, not caches.** Excluded from `state`: the eight DOM-only fields the
  design names, plus `pathQueries` (design), plus `sprites` (it holds the live atlas Image — a
  JSON copy would replace it with `{}`), `rnd` (a closure, rebuilt from the envelope's
  `seed`), `mapEpoch` (the design recomputes it on load, so storing it would fight the bump)
  and `autosaveAt` (T3's save schedule).
- **Object references become ids.** `Game.selection` and `Game.groups[*]` already hold unit
  ids; `Game.selectedBuilding` and `projectiles[].t` hold live objects, so they are stored as
  ids (`makeUnit` and `makeBuilding` share `Game.nextId`, so ids are unique across both) and
  relinked on load. A parsed `unit.order.src` would be a dead number where the live one is a
  getter onto `world.amount` / `b.field`, so `harvest` / `go_deposit` orders rebuild it
  through `sourceFromTile` / `sourceFromFarm`.
