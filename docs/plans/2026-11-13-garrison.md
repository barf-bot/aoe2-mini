# Garrison (housing units in buildings)

Status: in progress

## Design

Round: roadmap P1 item 5's second leftover — garrison mechanics. The bot leads the project:
work the roadmap in order and run each round without waiting for approval. The design below is
approved as written.

**What you'll see:** with own units selected, right-clicking a finished friendly building that
has capacity (town center, barracks, archery range, market, watch tower, guard tower, keep)
sends the chosen units in: they leave the field, the building's panel shows `Garrisoned n/cap`
and a `Leave` command per unit type (or `Leave all`). Clicking the building and pressing
`Leave` puts them back on walkable tiles around it, exactly where the standing-spot helper
places them, and an inside unit can no longer be picked or hit.

**How it works:** the capacity numbers already exist and are unused (`garrisonCapacity` on
every row of `data/buildings.json`, generated into `BLD`), so this round changes no data and
no art: only behaviour. `makeUnit` gains `garrisonedIn: null` (a unit id → building id link);
a unit with `garrisonedIn` set is skipped by `render.js` (not drawn), `economy.popCommitted`
keeps counting him (he still occupies the slot he always used), `sim.updateUnit` stops moving
and working him, and `findUnitAt`/`attackableAsEnemy` refuse him, so arrows and melee pass
over the building. The order is one new pure command, `garrisonUnits(Game, unitIds, b)` in
section 4 of `src/commands.js`: it toasts (not a friendly finished building, no capacity left
for the number ordered, a unit already inside) and otherwise, for the units that can go, sets
`u.garrisonedIn = b.id`; a unit that must walk there first keeps the `move` order to the
building's standing spot and is put inside on arrival by the existing arrival path in
`sim.updateUnit` rather than by a second timer. `leaveBuilding(Game, b, unitIds)` clears the
link and re-places each unit on `standingSpots` around the building. Save/load is free:
`encodeUnit` copies every key of the unit, so `garrisonedIn` rides along with no schema change
and `CFG.VERSION` stays where it is. `src/hud.js` renders the count and the `Leave` button in
the building panel the command grid already draws.

**Not in this round:** trade carts and land trade (item 5's last leftover), garrisoned units
shooting out of towers and keeps (AoE2 lets them; it needs the per-range attack work of item
4 first, so this round houses units without giving the building extra fire), enemy units
taking refuge in a burning or dying building, hitpoints regen inside, and the enemy AI
garrisoning its own villagers.

**How we check it:** four behaviour-only check files gain garrison sections, and no data or
generated file changes, so `tools/check-stats.mjs` and `assets/sprites.png` stay
byte-identical this round. `tools/checks/08-input.js`: right-clicking a friendly barracks with
two militia selected sets their `garrisonedIn` and issues `move` to the standing spot; a
building with one slot left takes one unit and toasts the second; an unfinished building and an
enemy building are both refused. `tools/checks/07-combat.js`: a garrisoned unit is not picked
by `findUnitAt`, is not `attackableAsEnemy`, keeps full hp while an arrow lands on his
building, and after `leaveBuilding` is hittable again. `tools/checks/09-hud.js`: the building
panel shows the `Garrisoned n/cap` line and the `Leave` button only when something is inside
(and the town center's existing villager count does not double-count occupants).
`tools/checks/10-reset-save.js`: save with units inside, reset, load, and the units come back
with `garrisonedIn` intact and the same population line. `node tools/headless-check.js -q` and
`node tools/render-preview.js` stay green.

**Hard constraints that survive from `AGENTS.md`:** the game stays one `index.html`; no
framework, no build step, no new image files (`assets/sprites.png` stays byte-identical this
round); `index.html` is patched, never rewritten; section 4 stays DOM-free; every task names a
proving check and the `Map of this file` banner stays truthful (`tools/audit-line-refs.js`).

Four places where the design's prose and the current tree disagree or leave a hole, and two
consequences worth writing down before any code; all settled here so the executor does not have
to guess:

- **There is no `findUnitAt`, and `attackableAsEnemy` cannot answer for a unit.** The tree's
  picking helpers are `pickUnit` (`src/input.js:4`) and `unitsInBox` (`src/input.js:22`) —
  `pickUnit` is what the design's `findUnitAt` means, and it is not on the `AoE2` export list
  yet (`src/main.js:6-20`), which `AGENTS.md` requires for a function a check calls.
  `attackableAsEnemy(b, team)` (`src/sim.js:314`) takes a *building*, so the unit half of the
  rule needs its own sibling: `targetableAsEnemy(u, team)` (append it after
  `attackableAsEnemy`, so nothing else in the file moves) becomes the one answer for
  "can a weapon point at this unit" and takes over the three hand-written predicates that
  already ask it — `autoAcquire` (`src/sim.js:175`), `orderForUnit` (`src/commands.js:12-13`)
  and `issueOrder` (`src/commands.js:54-55`) — plus the AI's prey picker `nearestEnemy`
  (`src/ai.js:38`), which is the only thing that could still land a swing on a unit the design
  says cannot be hit. `pickUnit`/`unitsInBox` get the same `!u.garrisonedIn` condition in place.
- **The link is written at command time, so the walk needs its own marker.** "Sets
  `u.garrisonedIn = b.id`" (the design's command + the 08-input check "sets their
  `garrisonedIn` **and** issues `move`") and "`sim.updateUnit` stops moving him, he is put
  inside on arrival" contradict each other unless the two states are separable: a linked unit
  who must not move can never arrive. Settled — `garrisonUnits` writes both `garrisonedIn`
  (that link *is* the reserved slot, so two orders in the same frame cannot overbook a
  building) and `u.order = { kind:'move', x, y, garrison: b.id }`; `updateUnit`'s new guard
  parks every linked unit *except* one whose live move order names his own building, and the
  existing arrival line (`src/sim.js:205`) retires that order to `idle`, which is what makes
  the arrival path the single place a garrison order ends — no second timer, as the design
  asks. Consequences, stated so nobody files them as bugs: the unit stops being drawn the
  moment the order is given (he walks in invisible, which is the design's "they leave the
  field"), and an arrow already in flight for him still lands (`updateProjectiles` is bound to
  its mark; the 07-combat case in the design is the arrow aimed at the *building*).
- **A building that goes away must evict.** The design's exclusions cover *enemy* units
  sheltering in a dying building, but says nothing about own units inside a building the player
  demolishes or that is razed: their link would dangle forever — invisible, unhittable, still
  costing population, unable to be ordered (`makeUnit`'s link has no self-healing path).
  Settled: `removeBuilding` (`src/entities.js:124`), the single door all three removal paths
  already use (`hitBuilding`, `cancelConstruction`, `demolish`), clears the link and the order
  of every unit whose `garrisonedIn` names that building before splicing it, re-placing them
  through the same `standingSpots` line `leaveBuilding` uses. No new field on the building, no
  `src/save.js` change.
- **Control-group recall is a second selection path the design does not mention.** `Game.groups`
  (`src/input.js:236` area, keys `1..9`) restores ids straight into `Game.selection`, and
  `selectedUnits` (`src/economy.js:124-131`) filters only `!x.dead` — so recalling a group
  would hand an order to a unit the design says cannot be picked, and `issueOrder` would give an
  inside unit a fresh move order. Settled: `selectedUnits` also requires `!x.garrisonedIn`,
  which is exactly the design's "the town center's existing villager count does not
  double-count occupants" clause expressed in the one function every consumer reads (the footer
  counts, the build buttons, `pickBuilders`, `issueOrder`). `popUsed`/`popCommitted` are
  unchanged — he keeps the population slot, he just cannot be ordered while inside.
- **The count and the buttons sit in different panels, because the frame says so.** "The
  building's panel shows `Garrisoned n/cap` and a `Leave` command per unit type (or `Leave
  all`)" splits along the uniform-HUD contract (`docs/plans/2026-11-12-uniform-hud-frame.md`):
  the number is an `infoHtml` body line (that panel owns title/body/hp, `src/hud.js:67-104`),
  the buttons are `commandsHtml` entries in the fixed grid (`src/hud.js:106-169`), and the
  click lands on the existing delegated `data-act` ladder (`src/input.js:244-255`). No new CSS,
  no new `hudState` value (`src/hud.js:38` already answers `building`).
- **Nothing new is drawn, so `preview.png` does not move.** The committed frame garrisons
  nobody; `tools/render-preview.js` is untouched and its output is byte-identical, which is the
  check that the render change is a skip and not a redraw (the tower round had a frame task
  because a footprint changed; here no footprint and no sprite changes).
